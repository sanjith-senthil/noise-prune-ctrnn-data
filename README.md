# Mod-Cog CTRNN Pruning Data Release

This data release contains the trained model checkpoints and frozen result
files used for the paper's quantitative claims. It is intended to pair with the
separate code release for reproducing the H=512 Mod-Cog CTRNN pruning analyses.

## Scope

The deposited model data are the 24 selected H=512 CTRNN checkpoints:

- 8 Mod-Cog tasks
- 3 independently trained model seeds per task
- selected final checkpoint from the 12,000-step two-phase training run
- checkpoint selection by validation sequence accuracy, with validation
  cross-entropy loss as the tie-break

The code that produced everything here is in the companion repository:

  https://github.com/sanjith-senthil/noise-prune-ctrnn-code

To reproduce a result, clone that repository and symlink this deposit's
`checkpoints/` directory at its root; every config loads checkpoints by a
relative path. Licensed CC BY 4.0; see LICENSE.

The deposit ships the trained networks for both hidden sizes: 24 at H=512 and 24
at H=1024, plus the six dm1/anti controls. Every checkpoint any deposited suite
loads is here, so each result can be regenerated from the code release.

The fixed evaluation and pruning-score batches are NOT deposited -- they are
2.9 GB of cache. They are not needed: the runner rebuilds and re-caches them
deterministically from the seeds recorded in every config (`eval_seed` 200000,
`score_batch_seed` 100000 + pruning seed), so a reproduction regenerates the
same batches rather than downloading them.

The deposited result files cover:

- the task-retention benchmark across 10-80% sparsity at hidden sizes 512 and
  1024, which backs the retention figures and the in-text retention values;
- amplification-factor distributions at 80% pruning;
- the capped-rescale quantile sweep;
- training-outcome summaries;
- the paper's statistical outputs.

**Read `SUPERSEDED.md` first.** The sampling rule's probability normalisation was
corrected in October 2026, and the six strategies that draw a Bernoulli mask were
re-run. `results/renormalized_2026_10/` holds the re-run and is the data the paper
reports; several older tables still contain pre-correction rows for those six
strategies, and `SUPERSEDED.md` names them file by file. The four deterministic
strategies were unaffected and their numbers are unchanged.

The Mod-Cog task generator itself is not deposited here. Calibration, scoring,
evaluation, and validation batches are regenerated by the code release from the
recorded config seeds rather than stored as raw batch tensors.

## Layout

- `checkpoints/`: 24 selected final model checkpoints plus original per-seed
  checkpoint manifests.
- `configs/`: training and analysis configs recording seeds and suite settings.
- `metadata/checkpoint_inventory.csv`: checkpoint paths, SHA-256 hashes, tensor
  keys/shapes, task, model seed, and selection rule.
- `metadata/source_file_map.csv`: mapping from source artifacts to release
  paths, including derived release tables.
- `results/task_retention/`: main seven-method task-preservation raw and
  summary tables, including spectral-abscissa summaries derived from the raw
  `post_rec_ct_abscissa` field.
- `results/amplification_factors/`: candidate-edge `1 / p_ij` distribution
  histograms and run-level summaries at 80% pruning. The release stores binned
  per-edge counts plus run summaries, not one row per candidate edge.
- `results/capped_rescale/`: q10-to-q100 capped-rescale raw rows and plot-level
  summaries with s.e.m. columns, including q-by-sparsity spectral-abscissa
  summaries.
- `results/training_outcomes/`: final selected-checkpoint outcomes by network,
  per-task summaries, and source training result CSVs.
- `results/statistics_2026_10/`: **the paper's statistics.** Mean retention curves
  with hierarchical-bootstrap intervals, the normalised 10-80% area-under-curve
  summary per method, the key comparisons with effect sizes and exact sign-flip
  p-values, and a before/after report on the normalisation correction. The code
  that produced them is in `code/` beside the tables.
- `results/statistics/`: descriptive statistics and the cap-sweep families from the
  earlier procedure. The Wilcoxon signed-rank and Holm-adjusted comparison tables
  that previously lived here have been removed: the paper now reports a
  hierarchical bootstrap over tasks with an exact sign-flip test, so those files
  described a procedure the manuscript no longer uses.

## Reproducibility Notes

Official task-preservation analyses use fixed held-out evaluation batches and
independent fixed pruning-score batches. The relevant seeds are recorded in the
analysis configs:

- score/calibration batch seeds: `100000`, `100001`, `100002`
- held-out evaluation batch seed base: `200000`
- evaluation seed: `0`
- training checkpoint validation batches: 64 batches during training
- task-preservation evaluation batches: 128 fixed held-out batches

Checkpoint tensors use the code release's `CTRNN` state-dict naming:

- `input_layer.weight`, `input_layer.bias`
- `hidden_layer.weight`, `hidden_layer.bias`
- `readout_layer.weight`, `readout_layer.bias`

These correspond to the input, recurrent, and readout weights/biases described
in the paper.

Spectral-abscissa summary tables report both the signed
`post_rec_ct_abscissa` value and `abs(post_rec_ct_abscissa)`. Stochastic
pruning seeds are averaged within each trained network first, then means,
s.d., and s.e.m. are computed across the 24 trained networks. Raw run means are
also included for auditability.

Some released rescale configuration rows contain a matched-diagonal flag. This
flag is nullified by the no-self-connection constraint and is inactive in all
reported runs. Some legacy source labels use `V-NP` for linearized noise-prune;
these labels are identical to `L-NP` as defined in the manuscript.

## Peer-Review Revision Additions (2026)

`results/revision_2026/` holds the artifacts generated in response to peer review. All of
them reuse the 24 trained H=512 checkpoints and the frozen evaluation and scoring batches,
so they are directly comparable to the original figures.

- `score_controls/`: uninformative-score and gain-matched controls (2,616 runs). Tests
  whether noise-prune's benefit is attributable to the covariance term rather than to
  stochastic masking with gain restoration. Includes plot points and the Holm-corrected
  15-comparison family.
- `low_sparsity/`: all seven methods at 10/20/30/40% pruning (1,752 runs), documenting the
  claim that methods other than random perform well below 50% sparsity. Also re-runs S-NP
  rescale at 50-80% to record the Bernoulli survivor count before the exact-density top-k.
- `noise_necessity/`: injected-noise sweep at sigma = {0.001, 0.25, 0.5, 1, 2} x sigma_nat
  (984 runs), separating noise-driven from task-driven covariance.
- `dm1anti_baselines/`: training outcomes for the two excluded tasks under the paper's
  protocol, with the six selected 12,000-step checkpoints under
  `checkpoints/tanh_h512_modcog_dm1anti_to12k_lr0006_seqbest_no_l2_seed{0,1,2}/`.
- `reference_tables/`: derived quantities cited in the revision -- chance level per task,
  floor-corrected retention with above-chance tests, recurrent-weight accounting, the
  theory gap in `K`, top-k binding, and the cap-value anchor.
- `statistics/`: significance tables regenerated with Hodges-Lehmann effect sizes and exact
  distribution-free confidence intervals, the task-clustered comparisons (ICC, variance
  components, leave-one-task-out), and per-task retention curves.
- `configs/`: the suite configurations used, so every run above is reproducible from the
  code release.
- `renormalized_2026_10/`: the re-run, one merged table per suite, with the
  configurations that produced them under `configs/`. Every run records
  `prune_prob_normalize_mode = bisect`.
  - `h512_p10_80` the four sampling strategies that do not read the cap, 10-80%,
    H=512 (2,328 rows), plus the 24 unpruned baselines
  - `h512_recap_p10_80` the two cap-dependent arms at 3.695 (1,152 rows)
  - `magopt_h512_p10_80` the same two arms at 4.549 (1,152 rows)
  - `magcap_h512_p10_80` the same two arms at 3.584 (1,152 rows)

  ### Which cap the paper reports, and why there are three

  Each score's cap is derived by one rule -- sweep the cap percentile, take the
  pooled optimum, then average that percentile's per-network value over 50-80%.
  Applied to each score separately the rule gives different numbers, because the
  magnitude score removes the small weights, loses more L1 mass than spectral
  gain, and needs more amplification headroom:

  | score | optimum | constant | swept in |
  |---|---|---|---|
  | noise | q50 | **3.695** | `capsweep_h512_p50_80` |
  | magnitude | q60 | **4.549** | `capsweep_mag_h512_p50_80` |

  **The paper's two capped arms therefore come from two different tables:**

  | paper arm | table | `prune_rescale_cap_value` |
  |---|---|---|
  | noise-prune + capped rescale | `h512_recap_p10_80` | 3.695 |
  | magnitude + capped rescale | `magopt_h512_p10_80` | 4.549 |

  The other rows in those two tables, and all of `magcap_h512_p10_80` (3.584,
  the magnitude score's q50, superseded once its sweep put the optimum at q60),
  are the off-diagonal cells of a {score} x {cap} grid. They are deposited
  because they are what establishes that the constant barely matters within a
  score -- each score gains under 0.004 of AUC from its own cap, an order of
  magnitude below the difference between the scores.

  ### Concatenating these tables

  The four H=512 tables that do not depend on the cap (`h512_p10_80` and the
  three control suites) partition the sampling arms cleanly: no strategy appears
  in two of them.

  **The three cap tables do not.** `run_id` is built from (task, network seed,
  arm, sparsity, draw) and does not contain the cap, so the same 1,152 `run_id`s
  appear in all three -- 2,304 of the `run_id`s in this directory are not unique
  across tables. Concatenating them blindly yields three rows per run at three
  different caps. Select on `prune_rescale_cap_value` as well as `run_id`, or
  take the two arms from the two tables named above.

  (The capped arms were also run at 3.8 before the recalibration. Those rows are
  not deposited, so 3.8 cannot be picked up by accident.)
  - `h1024_p10_80` the plain rescale rule at H=1024 (600 runs)
  - `h1024_rest_p10_80` the other three sampling arms at H=1024 (1,728 runs)
  - `capq50_h512_p10_80` the quantile-cap measurement the recalibration rests on
    (1,176 runs). The cap is the mean over 50-80% of each network's own median
    amplification: 3.823 before the correction, 3.695 after.

- `sharded_suites/`: suites the runner shards by (task, sparsity), shipped merged with
  the configs that produced them. These are read directly by the released figure and
  statistics code, so the analysis runs against the deposit without a missing path.
  - `fig3_lowsparsity_h512_p10_40`, `size_h1024_p10_40` the low-sparsity cells
  - `fixedcapfull_h512_p50_80`, `fixedcapfull_h1024_p50_80` the constant-factor cap
    arms. Both are sources for `final_style.py` and `paper_stats.py`. The H=512 table
    carries its 24 unpruned baselines once: the suite ran in two passes and each
    re-emitted them identically, and the staging script collapses rows that agree on
    every measured column while still refusing any `run_id` whose copies disagree.
  - `synaptic_h512_p50_80` gain restoration on the noise-prune mask at 50-80%:
    `match_l1_rowwise` (synaptic scaling, postsynaptic), `match_l1_colwise` (its
    presynaptic mirror) and `inv_density`. Without it the density-matched control on
    this mask could be quoted as a mean but not resampled for an interval.
  - `neuronwise_h512_p10_80` the same two per-neuron rules over the full 10-80% range
    on BOTH masks (600 runs, n = 24): the magnitude mask at every sparsity, and the
    noise-prune mask at 10-40%, which completes that mask's range against the suite
    above. The magnitude-mask rows supersede the 50-80% single-seed rows in
    `score_controls_round2/`, which they reproduce exactly where they overlap.

Per suite the deposit ships the **merged** raw rows and summaries rather than the eight
per-task shards the runner writes; the shards are intermediates carrying ~290 raw columns
each. For dm1/anti only the selected final checkpoints are deposited, matching how the
original 24 are handled.

## Checksums

`manifest.json` and `MANIFEST.sha256` contain SHA-256 checksums for every file in the
release staging directory. Both are regenerated by
`scripts/stage_revision_data_release.py` in the code release, which also stages the
revision artifacts. They currently carry 442 records. Two earlier pairs were
narrower: the original carried 70 and inadvertently omitted
`results/weight_distributions/`, so those seven files shipped unchecksummed, and the
first revision pair carried 234, before the renormalisation re-run was deposited.
